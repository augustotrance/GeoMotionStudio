## 1. Contexto

`CTR-GMS-PRJ-003` requiere guardar atómicamente, cargar, seleccionar y comprobar existencia. DOC-020 exige RPO cero para guardados confirmados, fallas inyectadas, integridad y recuperación no silenciosa. El piloto funciona localmente en navegadores de la matriz G6.

## 2. Alternativas

### A. `localStorage`

Se descarta por API sincrónica, capacidad limitada y ausencia de transacciones multi-registro.

### B. File System Access API como backend único

Se descarta por soporte desigual y modelo de permisos que no cubre todos los entornos. Podrá existir como adaptador futuro de exportación/importación.

### C. Wrapper externo de IndexedDB

Se difiere. Reduciría boilerplate, pero agrega dependencia y semántica propia antes de que la necesidad funcional esté especificada.

### D. IndexedDB nativo

Se adopta por persistencia local estructurada, API asíncrona y transacciones.

## 3. Decisión

1. IndexedDB nativo implementará el puerto de repositorio local.
2. Ningún módulo de dominio importa tipos o nombres de IndexedDB.
3. La base tendrá versión explícita y migraciones monotónicas.
4. El modelo material usa:
   - `documents`, clave `[projectId, generation]`;
   - `heads`, clave `projectId`; y
   - `recovery`, clave `[projectId, generation]`.
5. Cada envelope contiene `projectId`, `generation`, `formatVersion`, payload, SHA-256, estado y marcas técnicas permitidas.
6. Las generaciones son inmutables.
7. Guardar escribe nueva generación y cambia `head` en una única transacción `readwrite`.
8. Un aborto conserva el `head` anterior y mantiene Project `DIRTY`.
9. El acuse exige commit exitoso y lectura posterior cuyo digest coincida.
10. Al menos la generación confirmada anterior se conserva como candidata de recuperación.
11. Una recuperación se identifica como `RECOVERED`, muestra procedencia y requiere selección explícita antes de activarse como estado normal.
12. Quota, permiso, corrupción y versión no soportada producen errores tipados de DOC-019.

## 4. Atomicidad material

La atomicidad no depende de sobrescribir un único blob. Depende de que:

1. el documento nuevo exista completo e íntegro;
2. el puntero confirmado cambie solo dentro de la misma transacción;
3. ningún lector use una generación no referenciada como confirmada; y
4. el acuse ocurra después de verificar el corte confirmado.

Los candidatos huérfanos pueden limpiarse de forma segura porque no son `head`. La limpieza nunca elimina la generación confirmada ni su predecesora protegida.

## 5. Consecuencias

### Beneficios

- transacciones nativas;
- operación offline;
- sin dependencia adicional;
- conservación verificable del último confirmado; y
- recuperación explícita y auditable.

### Costes y límites

- IndexedDB es de bajo nivel;
- cuotas y políticas de expulsión varían por navegador;
- se requieren adaptadores de prueba y fallas inyectadas; y
- el usuario puede borrar datos del sitio fuera del control de la aplicación.

La interfaz futura deberá comunicar estos límites y podrá ofrecer exportación respaldada por otra SPEC.

## 6. Verificación

- pruebas de contrato con adaptador en memoria e IndexedDB real;
- 100/100 round-trips equivalentes;
- 50/50 fallas inyectadas preservan el `head` previo;
- digest alterado nunca se activa;
- migración fallida no cambia la versión utilizable;
- quota/permiso producen error tipado; y
- recuperación requiere aceptación explícita.
