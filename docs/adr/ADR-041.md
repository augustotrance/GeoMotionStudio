## 1. Contexto

ADR-019 establece Project como contexto raíz y coordinador. ADR-020 y ADR-021 preservan la propiedad independiente de Scene y Map. El piloto necesita guardar y reabrir un corte consistente que contenga datos aportados por esos tres módulos sin transferir a Project la propiedad de la semántica ajena.

## 2. Problema

Debe definirse qué es el Project Document, quién compone y persiste su envelope y cómo participan los módulos propietarios, evitando confundir la entidad Project con un archivo, crear copias mutables rivales o permitir que un formato físico gobierne el dominio.

## 3. Restricciones

- Project continúa como coordinador del ciclo de vida y la persistencia.
- Scene y Map conservan propiedad exclusiva de sus datos.
- El documento debe tener identidad de tipo y versión explícitas.
- El guardado debe representar un corte completo y validable.
- La tecnología de codificación no puede formar parte de la decisión estructural.
- Un documento inválido no puede reemplazar el contexto activo.

## 4. Alternativas evaluadas

### A. Project como objeto monolítico propietario de todos los datos

Simplifica superficialmente la serialización, pero viola la propiedad modular, duplica semántica y convierte Project en un dominio concentrador. Se descarta.

### B. Un archivo independiente por módulo

Preserva fronteras, pero introduce coordinación multiarchivo, estados parciales y recuperación compleja antes de que el piloto la necesite. Puede reevaluarse para escenarios futuros, pero se descarta para el primer incremento.

### C. Agregado documental versionado compuesto con snapshots de los propietarios

Project administra el envelope y la operación de persistencia; cada módulo aporta y valida su snapshot; el documento completo se confirma como una unidad. No confunde representación persistente con propietario vivo. Se adopta.

## 5. Decisión adoptada

El Project Document será un **agregado documental versionado**, no una entidad viva del dominio.

Project será propietario de:

- `documentType`;
- `formatVersion`;
- la composición del agregado;
- la validación del envelope; y
- la coordinación de guardado y reapertura.

Scene y Map serán propietarios de la semántica, validación y restauración de sus respectivos fragmentos. El Project Document contendrá snapshots inmutables del corte que se intenta guardar; no creará una segunda fuente mutable de estado.

El formato físico se decidirá posteriormente sin alterar este modelo.

## 6. Justificación

La alternativa adoptada:

- conserva ADR-019, ADR-020, ADR-021 y ADR-027;
- permite validar el conjunto antes de activarlo;
- facilita versionado y migraciones explícitas;
- hace posible una confirmación atómica desde la perspectiva del dominio; y
- desacopla el conocimiento del proyecto respecto del almacenamiento y la codificación.

## 7. Consecuencias

### Beneficios

- Ownership inequívoco.
- Un único artefacto lógico para guardar y reabrir el piloto.
- Versionado y compatibilidad verificables.
- Evolución independiente de módulos y tecnologías.

### Costes y límites

- Project debe orquestar snapshots y validación cruzada.
- Los módulos deben publicar contratos de snapshot.
- Cualquier nueva sección exige propietario, versionado y reglas de compatibilidad.
- DOC-020 fija las garantías de integridad y recuperación aprobadas para incorporación; la atomicidad material y las migraciones se deben concretar en G7.

### Riesgos controlados

- Un envelope excesivo podría filtrar internals: se prohíbe incluir objetos de motor, cachés, componentes o secretos.
- La duplicación de datos entre fragmentos produciría conflicto: cada campo debe tener un propietario único.
